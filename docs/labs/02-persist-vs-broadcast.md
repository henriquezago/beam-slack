# Lab 02 — Persist vs Broadcast Ordering

Track 2. Concepts: failure ordering, at-least-once vs at-most-once delivery,
idempotency, where side effects belong.

## The problem

A user types a message and hits enter. Two things have to happen: the message
must be written to PostgreSQL, and it must appear in every other connected
client. Those are two separate operations against two different systems, and
whichever you do second might not happen at all.

So which one goes first?

This looks like a style question and is not. It determines what a user sees when
the database is down, what happens when the channel process dies mid-send, and
whether two clients can end up with different histories.

## What already exists

`BeamSlackWeb.ChannelChannel` in `backend/lib/beamslack_web/channels/channel_channel.ex`.
`join/3` is finished. `handle_in("new_message", ...)` raises, and is yours.

You also have:

* `BeamSlack.Messaging.send_message/1`, which inserts and returns
  `{:ok, message}` or `{:error, changeset}`
* `BeamSlack.Messaging.list_messages/2`, which reads history with the sender
  preloaded
* `BeamSlackWeb.MessageJSON.data/1`, which is the exact payload shape the React
  client already renders. Reuse it rather than hand-rolling a map.
* `BeamSlackWeb.Authorization.fetch_writable_channel/2`, which enforces "posting
  requires channel membership"
* `BeamSlackWeb.ChangesetJSON.error/1`, which renders changeset errors

The React composer already pushes `"new_message"` over the socket and falls back
to HTTP when the push fails, so you can watch the fallback banner disappear as
you finish this lab.

## The contract

Client pushes `"new_message"` with `%{"body" => body}`. You reply with:

* `{:ok, message}` where `message` is `MessageJSON.data/1`'s shape
* `{:error, %{errors: %{field => [messages]}}}` for a validation failure
* `{:error, %{reason: "forbidden"}}` when the sender is not a channel member

And you broadcast `"new_message"` on the channel topic with the same message
shape. Lab 03's tests check who receives that broadcast.

Whether the sender's own connection also receives the broadcast is up to you. The
React client deduplicates by message id, so both choices work; be able to say
which you picked and why.

## Design questions

### 1. Broadcast first, or persist first?

**Persist, then broadcast.** Nobody is told about a message that does not exist.
The cost is latency: the client waits for a database round trip before anyone sees
anything. And the failure case is subtle rather than absent: if the process dies
after `Repo.insert` commits but before the broadcast, the message is durable and
silently invisible until someone refetches.

**Broadcast, then persist.** The UI feels instant. But now a failed insert has
already been announced. What do you do, broadcast a retraction? What does another
client do with a message that has no id, since the id is generated by the insert?
What happens when that client reloads and the message is gone?

**Both, asynchronously.** Hand the write to a `Task` and broadcast immediately.
Now you have two failure paths instead of one and no ordering guarantee at all.
What have you actually bought?

Work through each of these concretely:

* PostgreSQL is down. What does the sender see? What do other clients see?
* The insert succeeds but the connection dies before the reply. The client retries.
  How many messages exist now? What would make the retry safe?
* Two clients send at the same instant. Do they see the same order? Does the order
  they see match the order in the database, and does it matter?
* A client was disconnected for thirty seconds and reconnects. Where does it get
  the messages it missed, and does the answer depend on your ordering choice?

### 2. Where is the event emitted from?

The push arrives in the channel process. But the *decision* about what happens
when a message is created could live in several places:

* in `handle_in/3` directly, which is the least code and couples the web layer to
  the broadcast
* in `Messaging.send_message/1`, so every caller broadcasts, including the REST
  controller and a future Oban job. But now a context module knows about
  `BeamSlackWeb.Endpoint`, and tests that insert a message start broadcasting.
* in a separate function like `Messaging.create_and_publish/1`, leaving
  `send_message/1` pure
* emitted as a domain event that subscribers act on, which is Lab 03's territory

Note that `MessageController.create/2` already persists messages over HTTP, and
the React fallback path uses it. If the broadcast lives only in the channel, an
HTTP-sent message never reaches other clients. Is that acceptable? If not, where
does that push you?

### 3. What does a reply mean?

You are replying `{:ok, message}` to the sender. What has the sender learned?
That it was persisted? That others received it? That it was accepted for
processing? Pick one meaning and make the code honest about it, because the
client's optimistic UI depends on it.

## Failure questions

1. `Repo` is down. Does the channel process crash, or reply with an error? Which
   is better here, and what is the general rule you are applying?
2. The channel process crashes mid-send. What does the client observe? Does it
   retry? Should it?
3. A message is persisted but the broadcast is lost. How would you ever notice?
   What in the client eventually repairs it?
4. A message is broadcast but not persisted. Same questions.
5. The same message is sent twice because of a retry. What in the system makes
   that visible, and what would make it harmless?

## Acceptance criteria

* `mix test.labs` passes for `test/beamslack_web/channels/channel_message_test.exs`
  and `channel_broadcast_test.exs`.
* The React app sends over the socket, and the "realtime is unavailable" banner
  no longer appears.
* Two browser tabs on the same channel see each other's messages without a reload.
* You have written down your ordering choice and your answers to the failure
  questions above.

## Non-goals

* No delivery receipts, no read state, no message editing.
* No optimistic client-side ids. The client waits for the server's id.
* Do not add a queue or a retry library. If you find yourself wanting one, say why
  in one sentence and move on; Track 5 revisits it for notifications.

## Hints

* `Phoenix.Channel.broadcast!/3` raises, `broadcast/3` returns `:ok | {:error, _}`,
  and `broadcast_from!/3` skips the sending socket. The difference between them is
  the answer to a question above.
* A `{:reply, {:ok, payload}, socket}` return replies to the push. `{:noreply,
  socket}` does not, and the client's `receive("ok", ...)` never fires.
* `Ecto.Changeset` errors are already renderable: `ChangesetJSON.error(%{changeset:
  changeset})` gives you the `%{errors: ...}` map the tests expect.
